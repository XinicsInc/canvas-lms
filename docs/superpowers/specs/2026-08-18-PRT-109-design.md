# PRT-109 브레인스토밍 디자인 — 시험 응시 중 브라우저 네이티브 다이얼로그 제거

- 날짜: 2026-08-18
- 작성: brainstorming (superpowers:brainstorming) 결과를 정리한 디자인 문서
- Jira: [PRT-109](https://xinics.atlassian.net/browse/PRT-109) — Canvas, 시험 중 발생하는 브라우저 다이얼로그 제거하여 TrustLock 브라우저의 윈도우 OS 포커스/작업표시줄 문제 해소
- 분류: bounded 성격(기존 응시 플로우 수정)이나, xinics 워크플로우 요구에 따라 풀 디자인/spec 산출

> **갱신 기록 (2026-08-18, spec이 정본)**: 이 문서는 브레인스토밍 시점의 기록이며, 확정 계약은 spec(`2026-08-18-PRT-109-spec.md`)이 우선한다. 이후 확정 사항: ① Q2의 "실측 후 결정"은 Windows TLB 실측(beforeunload 네이티브 다이얼로그 미표시·리프레시 무음 차단)으로 **범위 제외 확정**(spec D4). ② §4-4의 "만료 시 확인 모달 닫고 즉시 제출"은 현행 만료 흐름 유지(설정에 따라 times_up 10초 카운트다운 후 제출 또는 `end_at` 폴백)로 대체(spec D5/R8). ③ UJS 계열 링크(`data-method` 등)는 로드 순서 비결정성으로 모달 인터셉트에서 제외하고, user content(퀴즈 설명·문항·답안·해설) 영역은 `#quiz-instructions`·`#questions` 서브트리 기준으로 UJS 트리거 속성을 본문 노출(`.loaded`) 전에 중화한다(spec D2). ④ 보조키(ctrl/cmd/shift) 클릭은 새 탭이므로 이탈 경고 인터셉트에서 제외한다(spec D2). ⑤ 재발행 방식이 최초 클릭과 재개 클릭에서 클릭 파이프라인을 각 1회 실행하는 점은 명시적 동작 변경으로 위험 수용했다(spec D2). ⑥ 구현 후 수동 QA에서 확인된 jQuery UI 다이얼로그 버튼의 Space 미동작은 Canvas 전역 선재 결함으로, 이번 범위 밖이며 별도 이슈로 분리한다(spec §11).

## 1. 문제 이해

TrustLock Browser(TLB)에서 브라우저 네이티브 `alert`/`confirm`/`prompt`가 OS 네이티브 다이얼로그로 처리되면서 Windows에서 작업표시줄 노출·포커스 이탈·타 앱 노출이 발생한다. Canvas 퀴즈 응시 중 이런 네이티브 다이얼로그가 표시되는 경로가 있어, 이를 페이지 내부 UI 다이얼로그로 교체한다.

코드 실측(2026-08-14 분석 + 2026-08-18 재검증, Explore 에이전트 2회):

**Canvas 2020 (`/data/canvas`, 이 저장소)** — 응시 중 네이티브 다이얼로그는 전부 `public/javascripts/take_quiz.js` 한 파일에 있음:

| 지점 | 위치 | 트리거 | i18n 키 |
|------|------|--------|---------|
| 링크 이탈 confirm | take_quiz.js:637 | 응시 중 `<a>` 클릭 (no-warning/파일 미리보기/해시 앵커/.ui-dialog 내부 제외) | `confirms.navigate_away` |
| 제출 confirm | take_quiz.js:914 (분기 872–909) | `cant_go_back` 공란(Next), 미열람 문항 제출, 미응답 문항 제출 | `confirms.cant_go_back_blank`, `confirms.unseen_questions`, `confirms.unanswered_questions` |
| beforeunload 경고 | take_quiz.js:571–590 | 탭 닫기·새로고침·주소 이동 (제출 중/이탈 승인 후 제외) | `confirms.unfinished_quiz` |
| (참고) unload 백업 | take_quiz.js:591–612 | 실제 페이지 이탈 시 답안 동기 백업 POST | — |

- 모든 핸들러는 `#preview_mode_link` 부재 시(실제 학생 응시)에만 등록된다 (take_quiz.js:568).
- 응시 경로에 `alert`/`prompt` 직접 호출은 없음. 퀴즈 저작 화면의 alert/confirm은 "시험 중" 범위 밖.

**Canvas 2024 (`/data/canvas2024`, 별도 저장소)** — 동일 구조가 `ui/features/take_quiz/jquery/index.js`에 존재: 링크 이탈 confirm(:631), 제출 confirm(:924, 분기 878–921), beforeunload(:565–584), unload 백업(:585–606). i18n 키 동일. 2024에만 `confirms.file_upload_in_progress` 제출 분기(:916–921)가 추가돼 있음. React/InstUI 모달 미도입 — jQuery UI 관용구 그대로.

**페이지 내부 모달 선례(양쪽 공통)**:
- `element_toggler` + `data-turn-into-dialog` 관용구 — `_cant_go_back_warning.html.erb`(응시 시작 경고). 엔진: 2020 `app/coffeescripts/behaviors/elementToggler.js`, 2024 `ui/boot/initializers/activateElementToggler.js` (기능 동일).
- `#times_up_dialog`(시간 만료)·`#deauthorized_dialog`(재로그인) — `take_quiz.js` 내 jQuery UI `.dialog()` 직접 호출.

**TLB 플러그인(`gems/plugins/xinics_trustlock_browser/`)**: 순수 서버측(User-Agent 서명·`X-TLB-Session` 검증). 프런트 훅 포인트 없음 — TLB 조건부 프런트 동작이 필요하면 서버 판정을 뷰/ENV로 주입하는 배선을 새로 만들어야 함.

## 2. 탐색한 질문과 결정 (사용자 확인 완료)

### Q1. 적용 범위 — 2020만? 2020+2024 공통?

**결정: 2020+2024 공통 spec, 구현은 2020 먼저 (버전별 plan 분리).**

근거: spec이 고정하는 것은 버전 무관 동작 계약(어떤 다이얼로그를 어떤 UX로, beforeunload 정책)이며, 문서를 분리하면 정책 결정이 두 버전에서 갈라질 위험이 있다. 2024 대조 실측 결과 두 구현은 같은 파일 계보로 호출 지점·i18n 키·가드 조건이 거의 1:1 대응하고, 차이(`file_upload_in_progress` 분기, ES 모듈/`useI18nScope`)는 plan 단계에서 흡수 가능한 수준. 공통 spec의 리스크가 낮음을 확인했다.

### Q2. `beforeunload` 처리 기준

**결정: TLB 실측 후 결정 — spec에는 조건부 결정으로 기록.**

`beforeunload`는 브라우저 보안상 커스텀 페이지 모달로 대체할 수 없다(탭 닫기·새로고침·뒤로가기를 스크립트가 가로챌 수 없음). 따라서 선택지는 유지/조건부 제거/전면 제거뿐이며, 전제 사실 — TLB(Electron 기반)가 `beforeunload`에서 실제로 네이티브 다이얼로그를 표시하는지(`will-prevent-unload` 처리 여부) — 를 실측한 뒤 결정한다:

- 표시함 → TLB 환경에서만 핸들러 미등록(서버 UA 판정을 ENV로 주입해 분기). 일반 브라우저는 유지.
- 표시 안 함(Electron 기본 동작) → 포커스 문제가 없으므로 범위 제외(현행 유지).

어느 경우든 `unload` 답안 백업 POST는 유지한다.

### Q3. confirm 대체 모달의 적용 조건

**결정: 전 브라우저 공통 교체 (TLB 감지 불필요).**

근거: 코드 경로가 하나라 단순하고, 일반 브라우저에서도 UX가 일관된다. 이슈 원문("Canvas 퀴즈 중에 표시되는 브라우저 다이얼로그를 변경한다")과도 부합. TLB 한정 교체(B안)는 기존 동작 보존이 최우선일 때의 대안이었으나 채택하지 않음.

## 3. 접근법 비교 — 대체 UI 구현 방식

| 후보 | 평가 |
|------|------|
| **A. `element_toggler`/`data-turn-into-dialog` 관용구** | 마크업에 미리 연결된 "클릭 → 열기" 전용. 이벤트 핸들러 중간에 동적 메시지(미응답 개수 보간)를 넣고 계속/취소에 따라 흐름을 재개하는 confirm 대체에는 구조적으로 맞지 않음. **탈락** |
| **B. jQuery UI `.dialog()` 직접 호출 (채택)** | `#times_up_dialog`/`#deauthorized_dialog`와 동일한 방식. `take_quiz.js`에 공용 확인 모달 헬퍼 1개 추가, 뷰에 숨김 div 템플릿. 새 의존성 없음, 같은 파일 안에 선례 2개, 2020/2024 동일 적용 가능. **채택** |
| **C. React/InstUI 모달** | 2020에는 해당 관용구 자체가 없고(응시 플로우는 양쪽 다 jQuery), 2024 응시 플로우도 React 미도입. 과도한 신규 도입. **탈락** |

## 4. 핵심 설계 — 동기 confirm의 비동기 모달 전환 계약

네이티브 `confirm`은 JS 실행을 멈추는 동기 호출이지만 페이지 모달은 비동기다. 두 지점 모두 "**일단 막고, 확인 시 재개**" 패턴으로 전환한다:

1. **링크 이탈**: 항상 `preventDefault` → 모달 표시 → [계속] 시 `alreadyAcceptedNavigatingAway = true` 설정 후 저장해둔 링크 동작 재개(`target`·`data-method` 속성 존중). [취소] 시 아무 동작 없음.
2. **제출 확인**: `preventDefault` → 모달 표시 → [확인] 시 재진입 방지 플래그를 세우고 폼 제출 재호출(핸들러가 플래그를 보고 경고 스킵). 기존 3분기(+2024 파일 업로드 분기) 메시지·우선순위 유지, 기존 i18n 키 재사용.
3. **재진입 방지**: 확인 후 재개된 동작은 경고 로직을 다시 타지 않아야 한다.
4. **비동기화 부작용 — 시간 만료와의 경쟁**: 네이티브 confirm은 JS를 멈춰 타이머까지 정지시켰지만, 모달은 그렇지 않다. 확인 모달이 열려 있는 동안 시간 만료 자동 제출이 발생하면 자동 제출이 우선하며 확인 모달에 막히지 않아야 한다(만료 시 확인 모달 닫고 즉시 제출).

문구는 기존 `confirms.*` 키를 재사용하고, 모달 제목·버튼 라벨만 신규 i18n 키를 추가한다(`ko.yml` 한글 번역 포함). 접근성은 jQuery UI `modal: true` 기본(포커스 이동·복귀, ESC=취소)을 따르며 기존 선례와 동일 수준으로 맞춘다.

## 5. YAGNI로 제거한 것

- TLB 감지 기반 confirm 분기(Q3에서 전 브라우저 공통으로 결정 — beforeunload 실측 결과에 따라 beforeunload에만 한정 도입 가능).
- 공용 confirm 모달의 범용 라이브러리화(이번 범위는 응시 화면 한정 헬퍼).
- 퀴즈 저작 화면 다이얼로그 정리(별도 이슈로 분리).
